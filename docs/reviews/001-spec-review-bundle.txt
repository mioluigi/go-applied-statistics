# Project Constitution: Modern Applied Statistics with Go (R versus Go)

> **Purpose.** The non-negotiable rules for this project. Every spec, plan, task and line of code is checked
> against them. A conflicting decision either changes or amends this file deliberately, with a note in
> `docs/decisions.md`.
>
> **Source of authority.** The Week 8 assignment and rubric (`docs/assignment-and-rubric.md`), carried forward
> from Week 7 (SFEDD v2.1, Articles 1–9) with changes for a project whose baseline is **a program in another
> language** and whose conclusion is **a cost recommendation**.
> Tags: **[C]** Coding · **[T]** Testing & metrics · **[D]** Design · **[Doc]** Documentation ·
> **[A]** Application. *New or changed this week* is marked **(W8)**.

---

## Article 1: Correctness before speed

1.1 **(W8)** The Go implementation is trusted only when its results are **comparable with R's on the same
input data**, by a rule written in the spec **before** measuring: exact agreement where the computation is
deterministic (for example the sample median), and agreement within a stated, justified tolerance where it is
random (for example a bootstrap standard error). A program makes the comparison. **[T]**
1.2 Speed and memory are reported only for an implementation that has passed 1.1. A faster Go variant must
give **the same results as the plain Go variant** for the same seed, or its difference is stated. **[T]**
1.3 Every number in the README (tables, headline figures, **and the cost-saving percentage**) is generated by
script from saved results and saved prices; prose that cites them is re-checked whenever results change. **[Doc]**
1.4 Concurrent code passes the race detector (`go test -race`) and gives **reproducible results for a given
seed whatever the number of workers**. **(W8)** **[T]**
1.5 **(W8)** Statistical code is tested against **answers known independently of the code**: closed-form
values, hand-computed small cases, and R's saved output. **[T]**

## Article 2: Idiomatic, readable Go (McConnell 2004, ch. 32) **[C]**

2.1 Go modules; `gofmt` and `go vet` clean.
2.2 Meaningful, specific names; not abstract, not overly long.
2.3 No useless temporary variables or intermediate results.
2.4 Functions do one thing; large blocks become small, named functions.
2.5 Plain `if/else` and `for`; distribute the NOT in complex Boolean expressions.
2.6 Every exported identifier has a doc comment; comments explain *why*.
2.7 Errors are returned and handled; **no `panic`** for bad input (empty data, non-numeric values, zero
replicates).
2.8 Every goroutine has an owner and an end; no goroutine outlives a call.
2.9 **(W8)** The R code is a deliverable too: readable, commented, runnable with one command, and
`set.seed`-reproducible.

## Article 3: Test-first, measured **[T]**

3.1 Failing test before implementation of every critical component; **mutation check** important tests (a
mutation that only breaks compilation does not count).
3.2 Standard `testing`; table-driven; tests need neither the internet nor R: R's results enter the Go tests
as **saved files with provenance**.
3.3 Benchmarks with `testing.B` and allocation reporting; CPU and memory profiles kept; the program logs what
it did (structured, to standard error).
3.4 **(W8) Fair comparison.** R and Go do **the same work on the same data on the same machine**: same
observations, same number of replicates, same statistic definition. The comparison states each side's
defaults (R is single-threaded unless told otherwise), **times the whole process as well as the computation**,
and reports single-core Go separately from multi-core Go. Medians of repeated runs; printing outside timed code.
3.5 **(W8)** Each performance improvement is **one measured step**: benchmark before, change, benchmark after,
both kept, so the README can say what improved the program and by how much.
3.6 Guards, scripts and acceptance checks are themselves tested on a passing and a failing case; exit codes
are tested on the **built binary**.

## Article 4: Clean, reusable design **[D]**

4.1 The statistical method lives in a **reusable package** with no printing and no `os.Exit`. The statistic
(median, mean, …) and the random source are **replaceable parts**, so the same resampling code serves another
statistic, another generator, and next week's assignment. The command-line program is a thin layer.
4.2 Sequential and concurrent runs use **the same code path**; only the worker count differs.
4.3 Pin every dependency version (`go.mod`, `go.sum`); `go.sum` is generated on Luis's Mac. R package
versions are recorded with the results. **(W8)**

## Article 5: Documentation and Git hygiene **[Doc]**

5.1 One `README.md` is the complete documentation: purpose, roles of programs and data, the package search
(R and Go), build, run, test, benchmark, results, experiences, recommendation.
5.2 One task per commit, message starts with the task ID; specs, plan, tasks, reviews, decisions in the repo.
5.3 README **GenAI Tools** section; AI dialogs in `docs/ai-dialogs/` with a `README.md` index.
5.4 `scripts/acceptance.sh` is committed and passes on a **fresh clone** before submission. Checks that need
R say so and are skipped with a clear message where R is absent, never silently. **(W8)**

## Article 6: A finished, friendly application **[A]**

6.1 The README gives **instructions for creating** a macOS binary, a Windows `.exe` and a macOS `.app`, and
the scripts that do it.
6.2 The program **runs to completion with no arguments** on the committed data.
6.3 User input (data file, replicates, seed, workers) is validated; bad input yields a clear message and a
non-zero exit code.
6.4 A finished run tells the user, in plain words, what was estimated, from which data, and where any output

## Article 7: How we work with AI tools

## 3. Riskiest assumptions to test in phase 1 (recorded now, tested next)

1. **"Same seed gives the same random draws in R and Go."** Both can use the Mersenne Twister, but R
   scrambles the seed in `set.seed`, turns generator output into a uniform number its own way, and since R
   3.6.0 draws `sample` indices by rejection sampling. If draws differ, results are comparable
   **statistically, not bit for bit**, and the spec's comparison rule must say so.
2. **"Median means the same thing on both sides."** For an even number of observations R averages the two
   middle values; a Go library may not.
3. **"Go is faster and saves cloud cost."** The assignment's premise. R's `sample` and `median` run in
   compiled C; the gap may be smaller than assumed, and whole-process time includes R's start-up.

## 4. Inherited code, read before it is run

`r/original/run-bootstrap-median.R` (T. W. Miller, revised May 23, 2024) and its listing arrived in commit
`80060ad`. Reading it (running it is the Mac part, §7):

1. **What it computes.** 100 iterations × 4 sample sizes (25, 100, 225, 400) × B = 100 resamples of a
   Normal(100, 10) sample. For each sample it keeps the **mean of the B bootstrap medians**, and reports the
   **standard deviation of that mean across the 100 samples**. That is a Monte Carlo estimate of how the
   median varies from sample to sample. The textbook bootstrap standard error is different: the standard
   deviation of the B bootstrap medians **within one sample**. Both are legitimate; the spec must say which
   one each number is, and the R and Go programs must compute the same one.
2. **Its cost is mostly not statistics.** Each of the 40,000 resamples builds a one-row data frame and
   `rbind`s it onto a growing one. That is R's slowest idiom. A comparison of Go against this program measures
   data-frame handling more than resampling. A fair comparison (constitution 3.4) also needs an **idiomatic R**
   version (preallocated vectors, or the `boot` package).
3. **Only the symmetric case.** It draws from a normal distribution; the assignment's example asks for
   positively skewed, symmetric and negatively skewed shapes.
4. **Seed 9999, R's default generator.** The listing should be reproduced exactly on R 4.4.2 (prediction P1).

## 5. Dependency audit: `github.com/seehuhn/mt19937` v1.0.0 (the assignment's suggestion)

| Property | Finding (from its source) | Consequence |
|---|---|---|
| Algorithm | **64-bit** Mersenne Twister (MT19937-64: 312 words of 64 bits) | **Not R's generator.** R uses the 32-bit MT19937 (624 words). The same seed cannot give the same stream. |
| Seeding | `Seed(int64)` (Knuth-style initialisation), `SeedFromSlice` | R scrambles the seed with a linear congruential generator instead |
| Default | An unseeded generator uses a fixed default seed | Reproducible, but silently identical across runs |
| Concurrency | Not safe for concurrent use (documented) | One generator per worker |
| Licence | **GPL-3.0** | Importing it puts our program under GPL terms; an owner decision |
| Interface | `math/rand` `Source64` | Works with `math/rand` version 1 |

The assignment says the Mersenne Twister "is the random number generator algorithm used in R and Python".
True of the family; this package is a different member of it. Using it would give *a* Mersenne Twister, not
*R's* numbers.

## 6. Riskiest assumption tested: can Go draw R's bootstrap samples?

`docs/spikes/001-rparity/main.go` (standard library only, 130 lines) re-implements from the R sources the
three steps between `set.seed()` and `sample()`: the seed scrambling, `unif_rand()`, and the rejection
sampling of an index.

| Probe (seed 431) | R 4.4.2 on the Mac | Go spike in the workspace |
|---|---|---|
| `runif(3)` | 0.75096705253235996 0.58476094505749643 0.80907909828238189 | identical, all 17 digits |
| `sample(10, 5, replace = TRUE)` | 3 6 10 6 8 | identical |

Reproduce: `go run docs/spikes/001-rparity/main.go` and compare with `docs/spikes/env-mac.txt`.

**Result: assumption 1 of §3 is overturned in the favourable direction.** A Go program can draw exactly R's
resamples, so the bootstrap can be compared **number for number**, not only statistically. This rests on

Workspace timing of a study-shaped workload in plain Go (same resampling volume as the R program,
`sort.Float64s` for the median, 2 slow virtual CPUs): 0.65–0.72 s over three runs. The sort dominates, which
names the first performance steps: a faster sort or a selection algorithm, and no per-draw logarithm.

a tight tolerance for the mean.

### Limits of what was tested (conditions)

- R 4.4.2 with its default generator settings, on Apple silicon. An R older than 3.6.0, or
  `RNGkind(sample.kind = "Rounding")`, draws indices differently.
- n up to 100,000. For n ≥ 2^31 R switches to a different path; out of scope.
- Data that is exact in floating point (integers). Real data read from text must parse to the same doubles
  in both languages; see risk R2 in the spec.
- The `boot` package draws all indices in one call and assigns them to replicates in a different order than
  a `sample()` loop. Its result is expected to agree statistically, not digit for digit (untested).

# Spec 001: Bootstrap standard error of the median, in R and in Go

| Field | Value |
|---|---|
| Status | **DRAFT v1, 2026-11-14**, for Gemini spec review (R1) and owner decisions Q1–Q10 |
| Inputs | `docs/assignment-and-rubric.md` (S1–S12, M1–M2, G1–G9) · `docs/constitution.md` · `docs/spikes/001-environment-and-baseline.md` |

## 1. Problem

A research consultancy runs computer-intensive statistics in R and pays for the cloud time. It asks an
independent data scientist two questions: **how easy is it to use Go in place of R (M1)**, and **how much
cloud cost would that save (M2)**. We answer for one method from Gelman and Vehtari's list, *bootstrapping
and simulation-based inference*, in the form the assignment suggests: a **distribution-free estimate of the
standard error of the median** by bootstrap resampling, for symmetric, positively skewed and negatively
skewed data.

The answer has three parts, and each must be reproducible by a command:

1. **The same analysis in R and in Go, on the same data, with comparable results.**
2. **Time and memory of both**, measured the same way, with start-up separated from computation.
3. **A recommendation with a cost figure** derived from the measurements and from a cloud provider's saved prices.

The spike changed what "comparable" can mean: Go can reproduce R's random draws exactly, so for the same data
and seed the two programs can be required to give **the same standard error of the median, digit for digit**
(spike §6–§7). The spike also showed the course's jump-start R program spends most of its 5 seconds on data
frames, so the comparison needs an idiomatic R baseline as well (spike §4).

## 2. Users and use

## 3. Definitions (so R and Go compute the same thing)

- **Data set**: n observations x₁…xₙ, n ≥ 2, read from a one-column CSV file.
- **Median**: for odd n the middle value; for even n **the mean of the two middle values** (R's `median`).
- **Bootstrap resample**: n values drawn from the data set with replacement.
- **Bootstrap standard error of a statistic** (the textbook definition, Efron and Tibshirani 1993): draw B
  resamples, compute the statistic on each, and take the **standard deviation of those B values, with
  denominator B − 1**.
- The course's R program reports a different quantity (the spread, across 100 fresh samples, of the average
  bootstrap median; spike §4). It is run unchanged and reported as the course's baseline; it is **not** the
  quantity our R and Go programs compute, and the README says so.
- **R stream**: resample indices drawn exactly as R 4.4.2 draws them after `set.seed(seed)` with default
  settings. **Block stream**: replicates split into fixed-size blocks, each block with its own generator
  derived from the seed and the block number, so blocks can run on different cores.

## 6. Comparability rule (written before measuring; constitution 1.1)

| Quantity | R (`sample()` loop) against Go (R stream) | Against the block stream or `boot` |
|---|---|---|
| n | equal | equal |
| Sample median | **identical** (same double) | identical |
| Sample mean | relative difference ≤ 1e-12 | ≤ 1e-12 |
| Bootstrap SE of the median | **identical** (same double) | relative difference ≤ **10 %** at B = 1,000 |
| Bootstrap SE of the mean | relative difference ≤ 1e-12 | ≤ 10 % at B = 1,000 |

Why these numbers. Identity for the median: the same indices select the same values, and a median is a
selection (or one exact average), so no rounding can differ; the spike observed identity. 1e-12 for means:
summation order differs; the spike observed 4.5e-16. 10 % between different random streams: two bootstrap
runs with different draws differ by Monte Carlo error, roughly SE ÷ √(2B) ≈ 2.2 % of the SE at B = 1,000 for
a near-normal statistic; 10 % is about four of those and still catches a wrong formula (a denominator of B
instead of B − 1 is invisible at any tolerance, so that is covered by exact tests instead).

A second, independent check: for the symmetric (normal) data sets the bootstrap SE of the **mean** must be
within 10 % of s ÷ √n, where s is the sample standard deviation.
