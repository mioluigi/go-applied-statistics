3. Risky Code Review (Defects, Not Style)
RC-1: rrand.Generator.Index(n) advances PRNG state on n == 1
(diverging from R) and hangs on n <= 0
●​ Severity: Medium
●​ Where: rrand/rrand.go, function Index(n int) int (lines 93–108):​
Go​
// The number of bits needed to write n-1 equals ceil(log2(n)), R's bit count, and​
// costs no logarithm.​
bitCount := bits.Len(uint(n - 1))​
mask := uint64(1)<<bitCount - 1​
for {​
var candidate uint64​
for filled := 0; filled <= bitCount; filled += bitsPerDraw {​
candidate = candidate<<bitsPerDraw | uint64(generator.uint32()>>bitsPerDraw)​
}​
candidate &= mask​
if candidate < uint64(n) {​
return int(candidate)​
}​
}​

●​ Defect:
 1.​ When n == 1, bits.Len(uint(0)) is 0 (bitCount = 0). In R's src/main/RNG.c (R_unif_index), if
(dn <= 0) return 0.0; int bits = (int) ceil(log2(dn)); if (bits == 0) return 0.0;, so R returns 0
immediately without consuming any random word from the Mersenne Twister. In
rrand.Index(1), however, the inner loop condition for filled := 0; filled <= bitCount; filled +=
bitsPerDraw evaluates 0 <= 0 as true on its first pass, calling generator.uint32() once
before masking with 0 and returning 0! A test that only checks the return value of
Index(1) (0 == 0, as in docs/mutation-checks.txt line 18) misses that the generator's
internal state generator.next has advanced by 1 word relative to R.
2.​ When n <= 0 (e.g., n == 0), uint(n - 1) underflows to math.MaxUint (bitCount = 64),
uint64(1)<<64 - 1 overflows to math.MaxUint64, and if candidate < uint64(0) is never true,
causing an infinite loop.
●​ Property a test can check: After g := rrand.New(431), calling g.Index(1) must return 0
and a subsequent call to g.Float64() must equal rrand.New(431).Float64() (matching R's
set.seed(431); sample.int(1, 1); runif(1)), and calling g.Index(0) must return 0 (or
panic/error) immediately without hanging (if n <= 1 { return 0 } at the top of Index fixes
both).

RC-3: bootstrap.Replicates shares a single mutable resample slice
across statistics in a replicate
●​ Severity: Low
●​ Where: bootstrap/bootstrap.go, function Replicates (lines 60–64 and 85–90), and
main.go (line 154):​
Go​
// Every statistic sees the same resample, in the order given; a statistic that reorders its​
// argument therefore changes the order (not the content) seen by those after it.​
...​

●​ Defect: Because Statistic is documented as "It receives a scratch copy and may reorder

config.Workers - config.Replicates idle goroutines that each allocate an unused

[]Statistic{stats.MedianInPlace, stats.Mean}, cfg) and reversing the slice
[]Statistic{stats.Mean, stats.MedianInPlace} must return bit-for-bit identical float64 slices
for both statistics, and a statistic that zeroes its input slice (for i := range x { x[i] = 0 }) must
not alter the result of a second statistic evaluated in the same call.

5. Is the Cost Model Sound?
1.​ The "8 jobs at once" assumption in Scenario B:
○​ Not sound as a comparison between 1-worker and 8-worker Go: As detailed in §4
(Claim 1), dividing a single solo process's runtime by 8 assumes 100% linear
multi-process scaling with zero shared-resource contention (no L2/SLC cache
thrashing, no memory-bandwidth saturation, no OS context switching, and no disk I/O
contention). Comparing that idealized number against a measured 8-worker Go run
(which achieved a 7.4× speedup at 𝑛 = 100, 000 on real hardware) stacks the deck
against parallel Go.
 ○​ Omitted memory-tier constraint on multi-process R: Look at results/tables.md ##
memory at 𝑛 = 100, 000: R's boot package uses 564.6 MB mean peak footprint and
822.2 MB mean maximum resident set size per process (and r-loop uses 238.6 MB
Max RSS). Running 8 R boot processes concurrently requires 8 × 0. 82𝐺𝐵 ≈ 6. 6𝐺𝐵 of
RAM (and at 𝑛 = 300, 000 would exceed the 16 GiB RAM of c7g.2xlarge, or exceed the 2
GiB RAM of c7g.medium for a single job!), whereas 8-worker Go shares a single copy of
the dataset in memory and uses only 14.0 MB peak footprint (16.0 MB Max RSS) across
all 8 workers combined! That shared-memory advantage is a major reason to use parallel
Go on large datasets, yet the cost prose overlooks it.
2.​ Using Apple M1 Max laptop timings with AWS EC2 c7g (Graviton3) prices:
○​ Architecturally reasonable for a classroom study, with caveats: Choosing
c7g.medium (1 vCPU) and c7g.2xlarge (8 vCPUs) aligns the ARM64 instruction set
(arm64) and core count (8 performance cores on M1 Max ↔ 8 vCPUs on c7g.2xlarge).
However, an Apple M1 Max performance core (3.2 GHz, 400 GB/s unified memory) is
significantly faster per core than an AWS Graviton3 c7g vCPU (2.6 GHz Neoverse V1), so
absolute cloud runtimes and dollar costs on EC2 would be roughly 1. 3 × –1. 6 × higher
than the laptop numbers. Furthermore, on-demand EC2 bills for instance uptime (per
second of VM wall-clock life), so Scenario A's per-job cost (whole-process time × hourly
price) only holds if a continuous batch queue keeps the c7g.medium instance
approaches 100% utilization (otherwise idle time between jobs dominates the bill).
3.​ Does the "percentage saved" answer the consultancy's question (M1 + M2)?:
○​ Only when paired with the dollar figures and break-even job counts: A headline of
"Go saves 45.8 % to 96.8 % of the compute cost" sounds massive in isolation, but
results/tables.md ## cost reveals that 96.8% of a 𝑛 = 100 job is $1.64 saved per million
jobs (610,863 jobs to save one dollar!), and 45.8% of an 𝑛 = 100, 000 job is $20.43
saved per million jobs (48,958 jobs to save one dollar).
○​ In README.md §"Effort: how easy is it?", the Go implementation required 1,755 lines of
Go code and tests (630 code + 1,125 test lines) compared to 36 lines of base R. Even if
a senior engineer writes and validates the Go port in two days (~1, 500–2,500 of
engineering time), recovering $2,000 requires ~100 million runs at 𝑛 = 100, 000 (or
~1.2 billion runs at 𝑛 = 100)! The table in ## cost wisely includes "Jobs to save one
dollar", which is the exact metric needed to connect M1 and M2, but the
Recommendation section at the top of README.md should cite those concrete dollar
and job-count thresholds so management sees immediately why small-scale migration
loses money on engineering time.
